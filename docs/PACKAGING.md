# دليل التغليف (PKGBUILD) — توليد sha256sums الحقيقية بعد وسم الإصدار

## المشكلة

`PKGBUILD` كان يحمل `sha256sums=('SKIP')` — مقبول فقط أثناء التطوير،
وخطر عند النشر: skip يعني أن makepkg لا يتحقق من سلامة المصدر،
فأي تلاعب أو تلف في الأرشيف المنزَّل يمر بصمت.

ملاحظة: المصدر هنا **أرشيف tarball من وسم إصدار** (وليس git clone)،
لذلك `makedepends=('git')` أُزيل — لا يوجد أي استخدام لـ git في
مراحل البناء.

## الخطوات المعتمدة لإصدار جديد

```bash
# 1) حدّث pkgver في PKGBUILD (مثال: 1.1.0 → 1.2.0) واعمل commit

# 2) وسِم الإصدار وادفع الوسم
git tag -a v1.2.0 -m "manjaro-care v1.2.0"
git push origin v1.2.0        # ينبغي أن يعمل بعد رفع الفرع من جهازك

# 3) ولّد البصمة الحقيقية (أحد الخيارين)
updpkgsums                    # يجلب الأرشيف ويحدّث PKGBUILD تلقائياً
# أو يدوياً:
curl -L "https://github.com/DrAbdulmalek/manjaro-care/archive/refs/tags/v1.2.0.tar.gz" \
  | sha256sum

# 4) ضع البصمة في sha256sums واعمل commit: "chore: sha256 for v1.2.0"

# 5) تحقق أن البناء سليم محلياً قبل النشر
makepkg -f
namcap PKGBUILD               # فحص أخطاء التغليف (اختياري لكن مُوصى به)
```

## لماذا البصمة تتغير مع كل وسم؟

أرشيف وسم GitHub يحتوي اسم المجلد `manjaro-care-<version>` وطابع
الضغط — أي تغيير في الإصدار يغير الأرشيف كله، فالبصمة تُعاد توليدها
**مع كل إصدار** ولا تُنسخ من إصدار سابق.

## قاعدة ثابتة

`SKIP` مسموح فقط في فرع التطوير أثناء التجربة. أي دمج إلى `main`
يتضمن PKGBUILD بإصدار جديد يجب أن يحمل بصمة فعلية — حالة الاختبار
اليدوية: `makepkg -f` ثم `pacman -Qi manjaro-care` بعد التثبيت.
